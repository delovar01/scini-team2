# Архитектура и реализация Retriever для эксперимента «Отравленная лента»

## 1. Назначение

Retriever — компонент экспериментального RAG-стенда, который по пользовательскому запросу выбирает `top-k` наиболее релевантных Telegram-постов и передаёт их в контекст LLM.

В рамках проекта Retriever должен решать две задачи:

1. выполнять семантический поиск по корпусу Telegram-постов;
2. корректно работать в эксперименте с indirect prompt injection, где один из постов временно заменяется атакованной (`poisoned`) версией.

Внешний контракт Retriever сохраняется простым:

```python
search(query, k) -> list[tuple[post_id, text]]
```

Для экспериментальной подмены поддерживается дополнительный необязательный параметр:

```python
search(query, k, override=(post_id, poisoned_text))
```

При этом остальные части стенда не должны знать внутреннее устройство Retriever.

---

## 2. Исходная реализация

В первоначальной версии `run.py` использовался TF-IDF Retriever с cosine similarity.

Для каждого вызова `run_one()` происходило следующее:

```text
sample
  ↓
создание словаря всех документов
  ↓
подмена одного документа poisoned_text
  ↓
создание нового Retriever(docs)
  ↓
построение TF-IDF представления всего корпуса
  ↓
поиск top-k
```

Для TF-IDF и корпуса из 250 документов это было приемлемо, однако такая архитектура становится крайне неэффективной при переходе на neural embeddings.

Если механически заменить TF-IDF на embedding-модель, то для каждого экспериментального sample пришлось бы:

1. заново создавать embedding-модель или обращаться к ней;
2. заново кодировать все 250 документов;
3. после поиска уничтожать полученный индекс;
4. повторять те же действия для следующего sample.

При большом числе комбинаций:

```text
samples × models × defenses
```

основная часть времени тратилась бы не на эксперимент, а на повторное вычисление одинаковых embeddings.

Поэтому переход на embeddings потребовал не только замены алгоритма поиска, но и изменения жизненного цикла Retriever.

---

## 3. Требования к новой реализации

Были сформулированы следующие требования.

### Функциональные

- семантический поиск по русскоязычным Telegram-постам;
- возврат `top-k` документов;
- поддержка temporary override одного документа;
- возврат именно poisoned-текста, если атакованный документ попал в `top-k`;
- отсутствие изменения исходного корпуса после override;
- совместимость с текущим `run_one()` и остальным стендом.

### Архитектурные

- embedding-модель загружается один раз;
- базовый корпус кодируется один раз;
- одинаковые queries не кодируются повторно;
- одинаковый poisoned text не кодируется повторно;
- Retriever не знает о defense-режимах, CANARY, LLM, `topic`, `channel` или логике атак;
- Retriever отвечает только за retrieval.

### Экспериментальные

- результаты должны быть воспроизводимы;
- поиск должен быть максимально прозрачным;
- не должно возникать скрытого approximate-search поведения;
- положение атаки `start/middle/end` не должно искусственно теряться из-за обрезания длинного документа.

## 4. Выбор embedding-модели

Выбрана модель:

```text
intfloat/multilingual-e5-small
```

### Причины выбора

1. **Multilingual**  
   Корпус в основном русскоязычный, поэтому нужна модель, работающая с русским текстом без отдельного перевода.

2. **Retrieval-oriented модель**  
   E5 обучена для semantic retrieval, то есть соответствует схеме:

   ```text
   query → relevant passages
   ```

3. **Небольшой размер**  
   Для корпуса из 250 Telegram-постов нет необходимости использовать тяжёлую embedding-модель.

4. **384-мерные embeddings**  
   Представление достаточно компактное:

   ```text
   embedding dimension = 384
   ```

5. **Поддержка asymmetric retrieval**  
   Пользовательский вопрос и документ имеют разную структуру и длину. Это типичная retrieval-задача.

## 5. Префиксы E5

Для E5 query и document кодируются в разных ролях.

Запрос:

```text
query: Что нового в RAG?
```

Документ:

```text
passage: <текст Telegram-поста>
```

Эта деталь скрыта внутри Retriever.

Внешний код передаёт обычный вопрос:

```python
retriever.search("Что нового в RAG?", 3)
```

Retriever самостоятельно добавляет `query:`.

Аналогично каждый chunk документа перед кодированием получает `passage:`.

Это позволяет не связывать остальной эксперимент с особенностями конкретной embedding-модели.

---

## 6. Почему не используется vector database

Рассматривались Qdrant, Chroma, FAISS/HNSW и другие варианты.

От них отказались по следующим причинам.

Корпус содержит всего:

```text
250 документов
```

После chunking:

```text
331 chunk
```

Exact search по 331 вектору размерности 384 является очень маленькой вычислительной задачей.

Использование отдельной vector DB добавило бы:

- дополнительную зависимость;
- конфигурацию;
- сериализацию;
- управление индексом;
- возможный approximate nearest neighbor поиск;
- дополнительные точки отказа.

При этом практически никакого выигрыша в производительности для текущего масштаба не было бы.

Поэтому выбран обычный in-memory exact search.

## 7. Нормализация и similarity

Embeddings создаются с:

```python
normalize_embeddings=True
```

После L2-нормализации длина каждого вектора равна примерно `1`.

Диагностический тест подтвердил:

```text
норма min = 1.000000
норма max = 1.000000
```

Для нормализованных embeddings cosine similarity эквивалентна dot product.

Поэтому similarity вычисляется как матричное умножение:

```python
scores = embeddings @ query_embedding
```

Это простая и быстрая операция.

## 8. Первая архитектурная оптимизация: один Retriever на эксперимент

### Проблема

Исходный `run_one()` создавал новый Retriever для каждого sample.

Для embedding retrieval это означало бы повторное кодирование всего корпуса.

### Решение

Retriever переносится на уровень `main()`:

```text
main
  ↓
load posts
  ↓
create Retriever once
  ↓
encode base corpus once
  ↓
run_one(...)
  ↓
run_one(...)
  ↓
run_one(...)
```

А `run_one()` получает уже существующий Retriever.

### Результат

При тестовом запуске:

```text
5 samples × 3 defenses = 15 прогонов
```

сообщение:

```text
кодирование базового корпуса: 250 постов
```

появилось только один раз.

Таким образом исключено повторное вычисление неизменяемой части корпуса.

---

## 9. Temporary override вместо изменения базового индекса

В каждом атакованном sample один пост заменяется `poisoned_text`.

Неудачный вариант:

```text
replace base document
→ recalculate index
→ search
→ restore original document
```

Недостатки:

- mutable state;
- риск забыть восстановить документ;
- возможное влияние одного sample на другой;
- необходимость пересчёта базового индекса.

Вместо этого используется:

```python
search(
    query,
    k,
    override=(sample.post.id, sample.poisoned_text)
)
```

Retriever:

1. берёт уже готовые base embeddings;
2. отдельно кодирует poisoned-версию только одного документа;
3. временно заменяет score этого `post_id`;
4. выполняет top-k;
5. не изменяет `self.docs` и базовые embeddings.

Тест подтвердил, что после override исходный текст документа остаётся неизменным.

## 10. Кэширование

### Query cache

Один и тот же вопрос используется во многих комбинациях:

```text
sample × model × defense
```

Поэтому используется:

```text
query text → query embedding
```

Диагностический тест:

```text
5 → 6 → 6
```

Первый новый query добавил embedding в cache, второй идентичный query повторно модель не вызывал.

### Poisoned passage cache

Один и тот же poisoned sample также может запускаться под разными моделями и defense-режимами.

Используется:

```text
poisoned_text → chunk embeddings
```

Тест:

```text
0 → 1 → 1
```

Повторная обработка того же poisoned text использует уже готовые embeddings.

## 11. Обнаруженная проблема ограничения 512 токенов

Первая рабочая embedding-версия кодировала каждый Telegram-пост целиком.

Диагностическая проверка показала:

```text
36 / 250 постов > 512 токенов
14.4 % корпуса
```

Самые длинные посты достигали:

```text
1277 tokens
1038 tokens
1023 tokens
...
```

Следовательно, обычный truncation означал бы, что значительная часть некоторых документов вообще не участвует в retrieval representation.

Это особенно критично для данного эксперимента.

Атаки вставляются в позиции:

```text
start
middle
end
```

При документе длиной около 1000 токенов и embedding-лимите 512:

```text
start  → почти всегда виден Retriever
middle → зависит от длины документа
end    → часто полностью обрезается
```

В результате эксперимент мог бы случайно измерять не только влияние позиции indirect prompt injection, но и факт попадания этой позиции в первые 512 токенов embedding-модели.

Это является потенциальным смешивающим фактором (`confounding factor`).

Поэтому архитектура была дополнительно изменена.

## 12. Document chunking

Документы теперь разбиваются по токенам.

Параметры по умолчанию:

```text
chunk size = 400 tokens
overlap    = 50 tokens
```

### Почему 400

Модель имеет ограничение контекста около 512 токенов.

Использование 400 токенов:

- оставляет запас под `passage:` и специальные токены;
- исключает обрезание chunk внутри модели;
- сохраняет достаточно большой контекст.

### Почему overlap 50

Без overlap смысл может быть разорван на границе:

```text
chunk 1:
... Retrieval Augmented

chunk 2:
Generation позволяет ...
```

Overlap копирует часть контекста в соседний chunk и уменьшает риск потери информации на границе.

---

## 13. Результат chunking на текущем датасете

После перехода на chunking:

```text
250 постов
→
331 chunk
```

Количество multi-chunk документов:

```text
64
```

Самый длинный документ:

```text
seeallochnaya_0022
1273 tokens
4 chunks
```

Все chunk embeddings:

```text
shape = (331, 384)
```

Все они нормализованы:

```text
min norm = 1.000000
max norm = 1.000000
```

Таким образом весь корпус помещается в embedding representation без удаления хвоста длинных документов.

## 14. Document-level aggregation

После chunking поиск выполняется по chunks, но внешнему RAG нужны документы.

Нельзя возвращать:

```text
post_A/chunk_1
post_A/chunk_2
post_A/chunk_3
```

как три разных результата.

Поэтому similarity сначала считается для каждого chunk:

```text
query ↔ A1 = 0.38
query ↔ A2 = 0.84
query ↔ A3 = 0.57
```

Затем вычисляется document-level score:

```text
score(post_A) = max(0.38, 0.84, 0.57)
              = 0.84
```

После этого `top-k` строится уже по `post_id`.

### Почему используется `max`

Для retrieval достаточно, чтобы в документе существовал один сильно релевантный фрагмент.

Если использовать average:

```text
(0.38 + 0.84 + 0.57) / 3 = 0.60
```

сильно релевантный fragment будет искусственно разбавлен нерелевантными частями длинного документа.

`max` лучше соответствует задаче:

> существует ли внутри этого Telegram-поста фрагмент, релевантный запросу?

---

## 15. Chunking и poisoned override

Для base corpus chunks и embeddings создаются один раз.

Для attacked sample:

```text
poisoned_text
  ↓
token chunking
  ↓
encode only poisoned chunks
  ↓
max similarity for this document
  ↓
temporarily replace score of original post_id
```

Остальные документы не пересчитываются.

Таким образом chunking не отменяет предыдущую оптимизацию.

---

## 16. Почему Retriever возвращает полный документ

Поиск выполняется по chunks, но интерфейс возвращает:

```python
(post_id, full_text)
```

а не сам найденный chunk.

Причина — текущий эксперимент исследует indirect prompt injection внутри Telegram-поста.

Если передавать LLM только отдельный chunk, мы изменим саму экспериментальную постановку: модель будет видеть уже не исходный пост, а его фрагмент.

Поэтому chunks используются только как retrieval representation.

После выбора документа LLM получает полный фактический текст документа.

Для атакованного документа это:

```text
poisoned_text
```

Для обычного:

```text
original text
```

## 18. Диагностические тесты

Проверялись следующие свойства:

- загрузка 250 posts;
- корректное построение chunk index;
- размерность embeddings;
- L2-нормализация;
- отсутствие duplicate `post_id` в top-k;
- semantic top-3;
- query cache;
- poisoned passage cache;
- temporary override;
- отсутствие изменения base corpus;
- обработка неизвестного override ID;
- сохранение payload, расположенного в конце самого длинного документа.

Все структурные проверки прошли.

---

## 19. Интерпретация теста с end-override

В диагностическом тесте в конец самого длинного документа добавлялась искусственная строка.

Тест подтвердил:

- payload попал в последний chunk;
- последний chunk был закодирован;
- poisoned representation была помещена в cache;
- base document не был изменён.

При этом synthetic document не обязательно обязан войти в top-3 по искусственному query.

Это не ошибка chunking.

В реальном эксперименте retrieval должен происходить в первую очередь по легитимному содержанию Telegram-поста. Attack payload является внешней вредоносной инструкцией внутри уже релевантного документа и не обязан сам делать документ релевантным пользовательскому вопросу.

---

## 20. Предупреждение tokenizer о 512 токенах

Во время диагностики может появляться сообщение:

```text
Token indices sequence length is longer than the specified maximum...
```

Оно возникает на этапе анализа полной token-длины исходного документа.

Это не означает, что длинная последовательность передаётся в embedding-модель.

Реальный inference выполняется уже после `_chunk_text()`, где каждый fragment имеет размер не более заданного `chunk_tokens`.

## 21. Разделение ответственности

Retriever намеренно не знает о:

- D0 / D1 / D2;
- CANARY;
- attack success;
- tool calls;
- LLM API;
- `topic`;
- `channel`;
- выборе natural query;
- экспериментальных метриках.

Его ответственность:

```text
query + corpus
      ↓
semantic retrieval
      ↓
top-k documents
```

Это позволяет независимо изменять методику формирования пользовательских вопросов без переписывания Retriever.

---

## 22. Формирование запросов

Первоначальная версия стенда формировала query из:

```text
channel + topic
```

где `topic` имел очень широкие значения вроде:

```text
ai
llm
ml
```

Команда признала эту логику временной заглушкой.

Для основного эксперимента планируется использовать пул естественных пользовательских вопросов для каждого topic.

Например:

```text
Какие новые модели для видео вышли?
Что нового в RAG?
```

Старый шаблонный query может быть сохранён отдельным прогоном как baseline для сравнения влияния формулировки запроса на:

- `retrieval_rate`;
- `ASR`;
- `ASR_if_retrieved`.

Важно, что эта логика находится за пределами Retriever.

Retriever получает уже готовую строку query.

## 24. Основные инженерные решения

| Решение | Обоснование |
|---|---|
| `multilingual-e5-small` | multilingual semantic retrieval, небольшой размер |
| 384-d embeddings | достаточно для маленького корпуса, низкие memory costs |
| `query:` / `passage:` | соответствует способу использования E5 |
| Exact search | всего 331 chunk; ANN/vector DB не нужны |
| Один Retriever | исключает повторную загрузку модели |
| Base encoding один раз | корпус почти полностью неизменен между samples |
| Temporary override | один attacked post без мутации base state |
| Query cache | один query используется многократно |
| Passage cache | один poisoned sample используется многократно |
| Chunk 400 | безопасный запас относительно max sequence length |
| Overlap 50 | сохраняет контекст на границах |
| Max aggregation | один релевантный fragment делает документ релевантным |
| Full text output | сохраняется исходная постановка RAG-эксперимента |

## 25. Ограничения текущего решения

### 1. Max-pooling может переоценивать длинные документы

Чем больше у документа chunks, тем больше возможностей получить случайно высокий similarity.

На текущем маленьком корпусе это приемлемо, но при масштабировании можно исследовать:

- top-N chunk aggregation;
- mean of best chunks;
- reranking.

### 2. Chunk size 400 / overlap 50 — инженерный выбор

Он обоснован ограничением модели и структурой корпуса, но не оптимизирован отдельным retrieval benchmark.

### 3. Нет специализированного reranker

Сейчас используется только bi-encoder E5.

Для текущего корпуса это разумно, но в будущем можно добавить cross-encoder reranking.

### 4. Base embeddings не сохраняются на диск

При каждом новом запуске `run.py` 331 base chunk кодируется заново.

Они не пересчитываются внутри одного эксперимента, однако между отдельными запусками процесс повторяется.

Для 331 chunk это приемлемо. При увеличении корпуса можно добавить disk cache.

### 5. Semantic quality пока проверялась вручную

Для полноценной оценки Retriever нужен размеченный набор:

```text
query → relevant post IDs
```

и метрики:

- Recall@k;
- MRR;
- nDCG.

Для текущей статьи основной объект исследования — indirect prompt injection, поэтому отдельный retrieval benchmark не является центральной задачей.

---

## 26. Возможные дальнейшие улучшения

Если корпус значительно вырастет:

1. сохранить base embeddings на диск;
2. перейти к FAISS или vector DB;
3. добавить retrieval benchmark;
4. протестировать несколько embedding-моделей;
5. оптимизировать chunk size;
6. добавить reranker;
7. исследовать влияние способа aggregation;
8. логировать retrieval scores в экспериментальные результаты.

Для текущего корпуса эти изменения не являются необходимыми.

---

## 27. Итог

В результате исходный TF-IDF Retriever был заменён на semantic embedding Retriever, при этом изменение было выполнено не как простая подстановка одной модели вместо другой, а как переработка жизненного цикла retrieval-компонента.

Главные изменения:

```text
TF-IDF
→ multilingual E5

new Retriever per sample
→ one Retriever per experiment

re-encode whole corpus
→ encode base corpus once

mutate/rebuild attacked corpus
→ temporary single-document override

single embedding per long document
→ overlapping token chunks

chunk-level search
→ max aggregation to document-level top-k

repeated query/poison encoding
→ in-memory caches
```

Диагностические тесты подтвердили корректность индекса, cache-механизмов, override, chunking и semantic retrieval.

Такая архитектура остаётся простой для корпуса из 250 постов, устраняет лишние вычисления и уменьшает риск методологического искажения эксперимента из-за ограничения embedding-модели по длине входа.
